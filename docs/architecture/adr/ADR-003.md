# ADR-003: Separate client access from provider credentials and pin model permissions

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `gateway`
- **Addresses:** [FR-001](../../functional-requirements/fr/FR-001.md), [FR-006](../../functional-requirements/fr/FR-006.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-04](../../quality-requirements/qr/QR-04.md)

## Context

A gateway caller needs permission to use selected models without receiving the server's provider API key.
The [server-key constraint](../../product-vision.md#con-04) and [US-07](https://github.com/iteam7/gateway7/issues/36) are existing sources for that boundary.
The implementation in reviewed, merged [PR #90](https://github.com/iteam7/gateway7/pull/90) protects both chat entry points and model discovery.
The options below explain the current implementation and do not claim an undocumented Customer verdict or prior design meeting.

The evidence is the [access controller](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/auth.py), [HTTP boundary](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/app.py), [model pinning](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/pipeline.py) and [provider transport](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/providers.py).
[FR-001](../../functional-requirements/fr/FR-001.md) keeps the provider credential on the server; [FR-006](../../functional-requirements/fr/FR-006.md) fixes the client/model gate and filtered discovery, while [QR-03](../../quality-requirements/qr/QR-03.md) and [QR-04](../../quality-requirements/qr/QR-04.md) constrain diagnostic exposure and SDK interoperability.

## Considered Options

- **Separate gateway tokens and per-client model allowlists.** Resolve credentials and permissions at startup, then authenticate and authorize each protected request before policy or provider work.
- **Give callers the provider key or accept their own upstream keys.** This moves provider-account authority to callers and expands credential handling beyond the current server-owned-key scope.
- **Authenticate only an SDK-compatible route.** This would leave the native route as a bypass; both routes must use the same boundary.
- **A persistent identity service with registration and token-management APIs.** This supports a broader account lifecycle but introduces a database and management surface that the configured-client pilot does not provide.
- **Carry the authorized model inside middleware-editable request data.** This couples content policies to access decisions; keeping the selected model outside that interface removes that mutation path.

## Decision Outcome

Chosen option: separate gateway tokens and per-client model allowlists, with the selected model outside middleware-editable payloads.
This applies the same access boundary to native and compatible routes without handing upstream account authority to callers or adding a persistent identity service.
Configuration names client-token environment-variable references and model allowlists, keeping provider credentials separate.
Startup validates token values, rejects duplicates and reuse of the provider key, and stores client-token digests with immutable permissions in the access controller.
This is not a claim that raw secrets disappear from process memory: environment variables and the provider adapter's request headers still contain credentials.
Trusted Python middleware shares that process and is not isolated from them.

`/chat`, `/v1/chat/completions` and `/v1/models` share authentication.
Missing, malformed or unknown tokens return 401; a disallowed model returns 403 before company middleware or provider invocation.
Model discovery lists configured permissions rather than querying or promising access at the provider.
The selected model travels separately from plugin payloads and is used as a request-local adapter value, avoiding shared-model mutation between concurrent calls.

Each gateway process selects one provider; real adapters validate the allowed official HTTPS origin and bounded model identifier, follow no redirects and make no automatic retries.
The client-facing compatibility is the [documented nonstreaming text subset](../../api.md#supported-compatibility-subset), not every OpenAI feature.
Provider errors are mapped to safe gateway-owned responses rather than echoing credentials, request text or upstream bodies.

This choice was put in force by the merge of PR #90 on 25 October 2026 after [DeniBorsh's implementation review](https://github.com/iteam7/gateway7/pull/90#pullrequestreview-5643522171).
Accepted records that existing access boundary; it does not attribute review of this ADR text or a new acceptance verdict to that earlier reviewer.

## Consequences

- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** callers use gateway credentials, provider keys remain server-held, and safe gateway-owned logs, metrics and errors avoid printing either credentials or message text.
  The scenario uses the shipped middleware; arbitrary installed Python is trusted, and the required search of captured allowed, denied and failing outputs is separate evidence.
- **Compatibility / Interoperability — [QR-04](../../quality-requirements/qr/QR-04.md):** the gateway token fits the SDK's API-key parameter and the authorized model reaches the same pipeline through the compatible route.
  The supported nonstreaming text call can retain the application's request flow, while streaming, tools, multimodal content and unsupported controls are explicitly rejected rather than silently ignored; this does not claim support for all OpenAI requests or replace the scenario's SDK check.
- **Administration cost:** token rotation, revocation and permission changes take effect only after restart; there is no token-management API, persistent user database, quota or rate-limit system.
- **Operational boundary:** `/health`, `/ready` and `/metrics` are intentionally unauthenticated, and the local monitoring stack is not a public authenticated control plane; shared deployment needs HTTPS and restricted infrastructure access.
- **Trust limit:** model pinning and secret-free plugin arguments constrain the supported interface, not arbitrary trusted Python code with process access.
- **Diagnostic limit:** gateway-owned logs and metric labels exclude credentials and content; installed modules remain responsible for their own output, and numeric usage is not a billing ledger.
