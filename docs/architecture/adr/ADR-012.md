# ADR-012: Keep One Profile-Aware Plugin Authoring Workflow

- **Status:** Proposed
- **Created:** 2026-11-17
- **Updated:** 2026-11-17
- **Containers:** `gateway`
- **Addresses:** [FR-003](../../functional-requirements/fr/FR-003.md), [FR-007](../../functional-requirements/fr/FR-007.md), [FR-008](../../functional-requirements/fr/FR-008.md), [FR-029](../../functional-requirements/fr/FR-029.md), [FR-030](../../functional-requirements/fr/FR-030.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-02](../../quality-requirements/qr/QR-02.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-06](../../quality-requirements/qr/QR-06.md)

## Context

The repository owner's [task #297](https://github.com/iteam7/gateway7/issues/297) requests a shorter path from a company policy to an installed, tested plugin, including instructions a coding agent can follow outside this repository.
The earlier generator creates a buffered Chat example and two fixtures, while native Responses and early delivery need separate hooks and manually assembled tests.
The phone and email policies repeat the same dispatch, structured-field checks and preparation hooks around their different text transformations.
The owner explicitly allows replacing the earlier authoring commands and fixture format; that permission does not require changing the installed middleware or transport contracts.
This record describes the proposed implementation and does not claim a team meeting or Customer acceptance.

## Considered Options

- **One project contract, profile-aware synthetic checks and an optional text-policy adapter.**
  A generated project owns its configuration, fixtures, declared profiles and local instructions, and uses the existing runtime contracts.
- **Add another check command beside the existing fixture command.**
  This duplicates the author's verification path and leaves uncertainty about which result to trust.
- **Generate every low-level hook independently in every company package.**
  This preserves repeated structured-field and early-delivery safety work even for a literal text rule.
- **Convert every request to Chat before applying a text callback.**
  This loses native item identity, executable data and consent boundaries.
- **Replace trusted modules with a new isolated plugin service or marketplace.**
  This changes deployment and security scope without resolving the immediate authoring workflow.

## Decision Outcome

Chosen option: one project contract, profile-aware synthetic checks and an optional text-policy adapter.
The project metadata in `pyproject.toml` identifies its module, relative configuration and fixtures, and declared delivery profiles.
Project paths remain inside the selected project directory.
`plugin test`, `plugin inspect` and `plugin dev` resolve that same project rather than introducing separate configuration discovery rules.
The authoring increment has one schema-2 fixture format and removes the earlier configuration/fixture command flags.
The unreleased package version and generated minimum dependency identify the build that actually supplies the new helper.

The optional text-policy adapter accepts an explicit phase, action and pure text transformation.
It implements middleware API v2 hooks using the existing Chat structured-field guards and native text traversal; it does not translate native Responses into Chat.
Protected structured matches deny a turn rather than rewrite an executable field.
Early hooks permit request-only policies and retain the existing refusal for response-dependent settings.
Advanced middleware continues to implement the raw API v2 contract, and provider transports retain their separate API v1 contract.

Synthetic tests run the actual pipeline for the selected Chat, tool, native or early profile in a bounded worker.
The worker receives no provider or gateway credentials and installs its networking and subprocess guards before importing project code.
Reports distinguish declared profiles, observed hook availability and the cases actually exercised; a negative unsupported-profile test does not certify support.
Inspection exposes safe descriptor metadata, settings schema and import provenance without returning configured values or arbitrary exception text.

The development command owns a loopback-only synthetic HTTP environment in a scrubbed child process.
It loads only the explicitly selected project's source, leaves project files untouched, and closes its servers and resources on interruption or startup failure.
Normal production serving continues to load installed packages and requires the established restart workflow.
Generated instructions and contract excerpts ship with the wheel so an author or coding agent does not need this repository checkout.

## Consequences

- **Maintainability / Testability — [QR-02](../../quality-requirements/qr/QR-02.md):** one helper and one fixture engine reduce repeated safety orchestration, but their profile matrix needs parity and installed-wheel tests.
- **Reliability / Fault Tolerance — [QR-01](../../quality-requirements/qr/QR-01.md):** a request denial and an unsupported requested profile must prevent provider work; the convenience layer cannot silently skip a policy.
- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** developer diagnostics expose core-authored locations and codes, while fixture values remain synthetic and local server credentials remain separate from real deployment secrets.
  Python guards catch accidental access and do not constitute an operating-system sandbox for hostile code.
- **Interaction Capability / Learnability — [QR-06](../../quality-requirements/qr/QR-06.md):** a generated project provides a short edit, test and local-request loop, while ordinary installation and advanced hooks remain explicit.
- **Compatibility cost:** the authoring CLI and fixture schema change together, with update instructions under Unreleased; no legacy authoring adapter or additional runtime ABI version is maintained.
