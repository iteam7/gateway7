# ADR-002: Run trusted plugins as guarded in-process middleware

- **Status:** Proposed
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `gateway`
- **Addresses:** Pending [task #91](https://github.com/iteam7/gateway7/issues/91): middleware behavior and quality requirements have not been published.
- **Decision:** [DEC-010](../../decisions.md#dec-010) permits restart-based plugin installation.

## Context

Company-authored policies must inspect both the request history and the returning answer while remaining replaceable without changing the core.
[DEC-014](../../decisions.md#dec-014) asks for an explainable execution/failure path, and [DEC-015](../../decisions.md#dec-015) asks for interacting plugins and an authoring walkthrough.
The middleware migration was requested in [DEC-016](../../decisions.md#dec-016) and delivered in the reviewed, merged [PR #90](https://github.com/iteam7/gateway7/pull/90).
The following comparison explains that implementation; it is not a new Customer decision or a fabricated record of a historical options meeting.

The [runner](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/pipeline.py), [loader](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/loader.py) and [plugin contract](../../plugins.md) define the actual enforcement boundary.

## Considered Options

- **One nested async middleware chain.** One instance owns its request and response logic around an awaited next handler; request order determines reverse response order.
- **Independent request and response hook lists.** The earlier API allowed separate ordering, but split one policy across hooks and made its return-path position a second configuration choice; API v2 deliberately removes that flexibility.
- **Separate plugin processes or services.** These can provide a different isolation boundary, but require transport, lifecycle and state-sharing contracts; that additional system is outside the current trusted-company-plugin scope.
- **Policies built into the core.** This would simplify some direct checks while making company policy changes core releases, contrary to the existing extension boundary.

## Decision Outcome

Chosen implementation: load trusted Python middleware at startup and nest the configured list around the provider.
With `[A, B, C]`, request work runs A/B/C and response work unwinds C/B/A.
Successful middleware must await `call_next` once in the same task while its invocation is active; a request policy can instead deny before forwarding.
The core validates payload boundaries and prevents a repeated, escaped or concurrent next call and a swallowed downstream error from becoming a successful response.

The guarantee is at most one gateway-owned provider invocation per pipeline run, not exactly-once delivery or billing at the remote provider.
A request denial causes zero calls; a response denial can follow one call and blocks delivery of its answer.
Provider usage and completion reason are snapshotted before middleware postprocessing, so transformed text cannot rewrite those observations.
Each request and configured instance has separate temporary context state, while instances and their resources are shared across requests.

Configuration and API descriptors are checked at startup, including disabled declarations; active middleware fails closed, and required instances cannot be omitted.
Installation and credential/configuration changes require restart.
The [offline runner](../../authoring.md) exercises the same loader and pipeline with synthetic fixtures, bounded worker execution and Python-level networking/process guards; it is not an OS security sandbox.

## Consequences

- **Execution cost:** plugins share process resources and privileges; operators must trust installed modules, which can access memory, environment, files and network.
- **Cancellation limit:** the overall deadline includes downstream time, while each middleware's own-work budget excludes its awaited next handler; cooperative asyncio cancellation cannot forcibly stop blocking or hostile code.
- **Policy effect:** an error or denial after forwarding cannot undo upstream work or make unknown usage zero; no automatic retry compensates for it.
- **Compatibility cost:** API v1 descriptors and independent hook lists are rejected, so existing plugins need the documented migration and a restart.

Acceptance needs the following records from #91, with their real identifiers linked in Addresses and here:

- Functional behavior for ordering, payload transformation, request/response denial and safe error outcomes, including zero provider calls before forwarding and no duplicate forwarding.
- Functional behavior for installing a module/configuration and testing its request/history/response expectations offline.
- A **Maintainability / Testability** scenario naming `gateway7/loader.py`, `gateway7/pipeline.py` and the offline execution path, with a reproducible check that fails on an incorrect plugin result.
- A **Reliability / Fault Tolerance** scenario for middleware failure or timeout, stating observable denial/error outcomes and the cooperative-execution environment rather than claiming an unimplemented hard-kill guarantee.

Until those links and their interpretation are reviewed, the record remains Proposed despite the implemented code.
