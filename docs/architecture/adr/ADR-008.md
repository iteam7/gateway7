# ADR-008: Keep Managed Client Policies And Usage In An Embedded Store

- **Status:** Proposed
- **Created:** 2026-11-15
- **Updated:** 2026-11-16
- **Containers:** `gateway`
- **Addresses:** [FR-021](../../functional-requirements/fr/FR-021.md), [FR-006](../../functional-requirements/fr/FR-006.md), [FR-019](../../functional-requirements/fr/FR-019.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

The repository owner's [task #288](https://github.com/iteam7/gateway7/issues/288) requests user, access and usage management through the existing operator console.
The configured-client boundary in [ADR-003](ADR-003.md) separates provider, client and operator authority, but its startup-only lifecycle leaves user changes in server configuration and secrets management.
The read-only console in [FR-020](../../functional-requirements/fr/FR-020.md) displays that state without providing a lifecycle.
[FR-021](../../functional-requirements/fr/FR-021.md) extends this capability while retaining the configured-client mode for existing installations.
This record describes the implementation proposed by task #288, without claiming a team meeting, Customer verdict or merge that has not occurred.
The subsequent PostgreSQL request is recorded in [ADR-009](ADR-009.md); this embedded store remains the explicitly selected SQLite compatibility option.

## Considered Options

- **Persist managed clients and usage in an embedded SQLite file owned by the gateway.**
  The existing Python runtime supplies transactions without introducing a separately deployed service or changing the provider path.
- **Rewrite the YAML configuration and environment variables from the console.**
  This would mix bootstrap secrets with user operations, retain restart-only enforcement and require safely rewriting operator-owned deployment files.
- **Keep console changes only in memory.**
  Restart would restore revoked credentials and erase usage, undermining the lifecycle the operator expects.
- **Add an external identity and accounting service.**
  This would support several gateway workers, but would introduce another deployed service, distributed policy publication and new operations beyond this single-process gateway.

## Decision Outcome

Chosen option: an opt-in embedded SQLite store, selected once through `auth.management_db` with a separate operator credential.
The gateway remains the container that owns this file; the store is not a new network service.
Existing installations without this setting retain their startup configuration and process-lifetime usage behavior.

First initialization imports configured clients and token digests once.
Thereafter the database is authoritative for client lifecycle, model permissions, request limits and additional middleware assignments.
An empty managed installation can start with no clients and issue its first client through the console.
Client tokens are generated by the server, returned once on creation or rotation, and represented by digests in the store.
Revocation removes the digest, suspension preserves the credential while disabling access, and deleted identifiers cannot be reused to merge a new account into historical accounting.

The separate operator capability protects every management operation before its body is read.
Writes also require a dedicated request header and reject cross-origin browser requests.
The browser holds credentials only in page memory and uses the same origin for all management calls.

Each client change is validated against provider model rules and the already loaded middleware instances before it is persisted and published to the running application.
Publication preserves existing admission leases and unrelated rate consumption; requests already running can finish through their captured pipeline, while subsequent requests use the current policy.
Additional client policies append to the configured shared baseline and cannot remove it.
Installing or reconfiguring middleware code and changing provider/bootstrap settings still require server-side deployment and restart.

Numeric provider observations are aggregated by client, model and UTC day in the same store.
Known input/output tokens remain separate from attempts without valid source usage.
Day-inclusive filters and CSV export support inspection without storing conversation content.
These aggregates do not implement the arbitrary timestamp interval in [FR-012](../../functional-requirements/fr/FR-012.md), monetary billing or distributed budgets.

## Consequences

- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** no raw client token or conversation content is written to the store, and snapshots omit credential references, provider origins and policy settings.
  Generated token responses are intentional one-time credential delivery to the authenticated operator; logs, metrics and errors retain their existing confidentiality boundary.
  File permissions and the private deployment volume protect identities and usage at rest; the SQLite file is not encrypted.
- **Deployment cost:** one process owns an exclusive database connection, and another worker sharing that file fails startup.
  A writable private volume and ordinary database backup discipline are required for persistent installations; losing the file loses managed identities and accounting.
- **Runtime cost:** small synchronous transactions serialize client publication and aggregate updates inside the existing process.
  The implementation does not promise multi-worker synchronization, billing accuracy or a hard token budget.
- **Compatibility cost:** the console must display whether its gateway uses managed persistence or the original read-only mode, including the actual restart behavior of usage counters.
  Accepted historical ADRs retain their original context; this optional extension does not rewrite their implementation evidence.
