# ADR-007: Read Gateway Operating Signals From OpenObserve

- **Status:** Proposed
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `gateway`
- **Addresses:** [FR-014](../../functional-requirements/fr/FR-014.md), [QR-05](../../quality-requirements/qr/QR-05.md)

## Context

[US-15](https://github.com/iteam7/gateway7/issues/175) needs an operator to find a failed request and read its duration aggregate.
[PR #193](https://github.com/iteam7/gateway7/pull/193) already implemented optional OTLP logs and a histogram from the same monotonic measurement.
[SLI-01](../../observability.md#sli-01) owns the aggregate and per-request queries; [QR-05](../../quality-requirements/qr/QR-05.md) owns their visibility deadlines.
This record proposes that existing design and its verification tooling for review; a passing local fixture is not a deployed staging test.

## Considered Options

- **OpenObserve with OTLP/HTTP.** Store structured logs and duration buckets in one backend, scoped by environment.
- **Separate log and metric backends.** Rejected for this slice because two operating stacks and query credentials add work without changing the required signal.
- **Local standard output only.** Rejected because a terminal log cannot provide the persisted five-minute P95 query the operator needs.

## Decision Outcome

Chosen option: retain the gateway's OTLP/HTTP export to self-hosted OpenObserve with one staging organization and one production organization.
Logs carry `request_id`, `route`, `outcome`, `status`, `error_code` and `duration_ms`; the histogram has only bounded `route` and `outcome` labels.
The histogram uses delta temporality, so the five-minute query sums the interval observations and includes the first failed request of a new series.
The staging QRT verifies a restricted client, requests a model absent from its allowlist, then reads that failure's exact log point and a numeric failure-series P95 through the backend APIs.
It makes no paid provider call and requires the operator to confirm the target; a supplied commit hash is an assertion to check against the selected deployment.
The [deployment runbook](../../deployment.md#telemetry-pipelines) owns installation and dashboard import steps.

## Consequences

- **Maintainability / Analysability ([QR-05](../../quality-requirements/qr/QR-05.md)).** A shared measurement connects one failed request with its aggregate without making the random request identifier a metric label.
- **Cost.** Export intervals, backend health and storage/query latency affect the visibility deadlines; only an actual run against deployed staging establishes that the requirement passes.
- **Cost.** Production has a separate organization and the same chart definition, but staging checks must never generate production test traffic.
