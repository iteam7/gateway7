# ADR-005: Collect provider streams before guarded agent delivery

- **Status:** Proposed
- **Created:** 2026-10-30
- **Updated:** 2026-10-30
- **Containers:** `gateway`
- **Addresses:** [FR-001](../../functional-requirements/fr/FR-001.md), [FR-003](../../functional-requirements/fr/FR-003.md), [FR-005](../../functional-requirements/fr/FR-005.md), [FR-013](../../functional-requirements/fr/FR-013.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-02](../../quality-requirements/qr/QR-02.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-04](../../quality-requirements/qr/QR-04.md)

## Context

[Task #153](https://github.com/iteam7/gateway7/issues/153) requests streaming provider API support with OpenCode as the agent harness.
The existing server-key boundary belongs to [FR-001](../../functional-requirements/fr/FR-001.md), and [FR-005](../../functional-requirements/fr/FR-005.md) requires answer checks before delivery.
The middleware contract in [ADR-002](ADR-002.md) awaits a complete provider-neutral response rather than a stream of deltas.
An agent also exchanges structured function calls and matching tool results, which [FR-013](../../functional-requirements/fr/FR-013.md) specifies separately from SSE framing.

This record describes the proposed implementation for that task.
It records neither a Customer verdict nor team acceptance of a new latency target.
The earlier Accepted access and middleware records remain historical records; this extension retains their credential, routing and terminal-failure boundaries.

## Considered Options

- **Wrap an ordinary full provider response in SSE.** This supplies client framing but does not use the provider's streaming endpoint requested by the task.
- **Relay provider deltas immediately.** This reduces the wait for the first client-visible content but can release a prefix before a full-response policy decides to deny the answer.
  Preserving full-response middleware would require a separate delivery mode and a streaming policy contract.
- **Collect and validate an actual provider stream, then emit checked SSE.** This retains the existing full-response middleware while supplying the streaming wire format the harness consumes.

## Decision Outcome

Chosen option: collect and validate an actual provider stream, then emit checked SSE.
The first provider implementation is OpenAI Chat Completions.
When a supported client request asks for streaming, the adapter sends `stream: true` upstream, assembles its text and function-call deltas, checks terminal completion, and returns one provider-neutral response.
Provider streaming is a transport choice pinned outside the middleware-editable request, like the authorized model.
The gateway does not retry or fail over a provider call.

The existing middleware chain checks the assembled response in reverse order.
Only after the whole chain succeeds does the HTTP layer serialize client SSE, including function-call deltas, the actual completion reason, requested usage and the terminal marker.
Provider or policy failures before release remain ordinary safe HTTP errors.
Downstream SSE is therefore buffered delivery: the client receives no generation-time tokens and no unapproved tool invocation.
This preserves the token-by-token exclusion in [BND-01](../../product-vision.md#bnd-01).

Function calls are structured data throughout the pipeline, not assistant text pretending to be a call.
The harness executes a permitted call locally and returns its result in a subsequent request with the same call identifier.
Gateway7 forwards that history but does not execute tools or keep a persistent agent session.
The initial contract supports one function call per turn, and explicitly rejects unsupported parallel, custom-tool and multimodal requests.
Claude and Gemini retain their existing nonstreaming text path; their streaming and tool requests fail before forwarding.

Middleware API version 2 keeps its awaited handler shape.
A descriptor must explicitly advertise support for tool payloads before an agent request may enter that chain.
The shipped policies inspect tool metadata and decoded arguments as well as ordinary text.
For structured fields, content-policy `block` and `redact` both deny the whole message on a match, while `log` forwards unchanged and records metadata only.
Email and phone masking also deny structured matches instead of rewriting executable arguments or schema text.
Ordinary message and tool-result text retains its configured masking or redaction behavior.
Provider-owned accounting and completion reason remain separate from policy-editable content, and final response validation includes the tool-call structure.

## Consequences

- **Reliability / Fault Tolerance — [QR-01](../../quality-requirements/qr/QR-01.md):** request-side denial still prevents provider work, and a denied or malformed assembled answer is not released as partial success.
  A completed provider call cannot be undone, and cancellation of trusted Python remains cooperative.
- **Maintainability / Testability — [QR-02](../../quality-requirements/qr/QR-02.md):** a bounded SSE assembler and typed function messages can be tested with fragmented synthetic HTTP responses and the same full-response middleware runner.
  A harness run against a scripted upstream proves that selected client scenario only; a live account check is separate evidence.
- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** tool arguments are checked before the harness can execute them, unsupported middleware fails closed, and errors and observations do not expose upstream bodies or credentials.
  Third-party middleware and transports remain trusted in-process code rather than a sandbox.
- **Compatibility / Interoperability — [QR-04](../../quality-requirements/qr/QR-04.md):** the existing nonstreaming SDK path remains a regression criterion while the explicit agent subset gains SSE and function-call framing.
  QR-04's original SDK scenario does not establish OpenCode compatibility; the exact harness version, configuration and observed scenario must be recorded independently.
- **Cost and scope:** full-response storage and validation remain necessary before client delivery, so this option provides no first-token latency improvement.
  Stream size, event size, input size and deadlines remain bounded; support for additional provider formats and live token delivery needs a separate increment.
