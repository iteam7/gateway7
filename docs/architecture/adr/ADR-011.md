# ADR-011: Publish Live Provider Snapshots With Encrypted Credentials

- **Status:** Proposed
- **Created:** 2026-11-16
- **Updated:** 2026-11-16
- **Containers:** `gateway`, `postgres`
- **Addresses:** [FR-025](../../functional-requirements/fr/FR-025.md), [FR-006](../../functional-requirements/fr/FR-006.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

[Task #295](https://github.com/iteam7/gateway7/issues/295) extends the operator workspace to the selected provider, model catalog, effective permissions and provider credentials.
The gateway currently selects one provider at startup and keeps its credential server-side.
A live change must preserve that boundary, survive restart and allow already-admitted requests to finish through their captured provider instance.

## Considered Options

- **Persist encrypted credentials and publish a validated replacement provider snapshot.**
  This supports live administration while keeping plaintext secrets out of database records and audit projections.
- **Write plaintext provider keys into the control document.**
  This would make database reads and backups expose the upstream account credential directly.
- **Close the current provider as soon as a replacement is selected.**
  Requests already using that client could fail midway through generation or delivery.
- **Introduce several providers and cross-provider failover.**
  This exceeds the selected single-provider scope and changes retry, accounting and access semantics.

## Decision Outcome

Chosen option: validate, persist and publish one replacement provider snapshot, with credentials encrypted using a server-supplied Fernet key.
The encryption key is bootstrap server configuration and is neither returned by the console nor included in a database backup.
The provider credential is decrypted only for adapter construction; state projections show credential presence and safe metadata, while audit records only that a credential changed.
Restoring encrypted state requires the same configured encryption key.

Provider changes use the same administrative revision and audit transaction as other control writes.
The candidate retains existing origin, transport and model-identifier validation before it can be activated.
Publication updates the effective configuration, access controller and request pipelines together without an intervening await.
The replaced provider is retired only after its captured admitted work and delivery ownership have drained.

Configured model names, catalog observations and effective client permissions are displayed separately.
Aliases resolve once to a canonical provider model before permission checks and remain outside middleware-editable request data.
An omitted model uses the client's permitted default when configured, otherwise the gateway default.
Connection tests are explicit operator actions, and their sanitized result records when the observation occurred without claiming continuous provider availability.

## Consequences

- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** database and backup contents hold encrypted provider credentials, while public errors, protected state and audit entries omit plaintext keys and encryption material.
  A missing or invalid encryption key prevents unsafe credential publication.
- **Deployment cost:** the service account must receive and retain the encryption key separately from its database and backups.
  Losing it prevents recovering encrypted provider credentials.
- **Runtime cost:** old provider instances can remain alive while their requests drain.
  The gateway still selects one provider for new work; this is not multi-provider routing or automatic failover.
