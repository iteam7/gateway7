# ADR-004: Configure provider transports through startup modules

- **Status:** Proposed
- **Created:** 2026-10-29
- **Updated:** 2026-10-29
- **Containers:** `gateway`
- **Addresses:** [FR-001](../../functional-requirements/fr/FR-001.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-02](../../quality-requirements/qr/QR-02.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

[Task #143](https://github.com/iteam7/gateway7/issues/143) asks for optional provider access through a proxy that fits the project's module-based extensions.
The provider adapter owns the server key and its one configured provider origin under [FR-001](../../functional-requirements/fr/FR-001.md) and [ADR-003](ADR-003.md).
The middleware chain owns message processing, not the provider HTTP client.
Proxy selection belongs to startup because a single provider client serves concurrent requests for the lifetime of the app.

This record proposes the transport extension implemented for review in that task.
It does not record a Customer decision or change the status of the existing Accepted records.

## Considered Options

- **A proxy field built into each adapter.** This is small, but repeats transport setup across provider formats and gives a company no module extension point.
- **Middleware that changes the provider client.** Request-time changes can affect concurrent requests and mix networking with the message-processing contract.
- **A module that creates the whole HTTP client.** This lets the extension replace redirect, timeout and environment handling that the gateway already owns.
- **A startup module that creates an async transport.** The provider keeps its client and wire-format checks while an installed module supplies the network transport once.

## Decision Outcome

Chosen option: a startup module that creates an async transport.
The proposed `provider.transport` setting names an importable module and its settings.
Its versioned `TRANSPORT` descriptor validates a strict settings model and supplies a synchronous factory returning `httpx.AsyncBaseTransport`.
This interface is separate from middleware API version 2: it has no `handle` or `call_next`, and its factory runs at startup rather than inside the request chain.

The shipped HTTP(S) proxy module reads the proxy URL from one explicit environment-variable reference at startup.
It supplies a verifying transport with no automatic retries or environment proxy discovery; HTTPS proxy and provider TLS both use explicit environment-independent trust settings.
The core still owns the client timeout, disabled redirects, allowed provider origin, provider credentials, bounded response processing and safe error mapping.
An unset transport keeps the existing direct client path.

The gateway owns a valid transport after its factory returns it.
If client construction fails, startup closes that transport; after successful construction, the provider client owns its close operation.
Each app gets its own instance, reused by its requests and closed during the existing cooperative lifespan cleanup.
A custom factory must clean up resources it allocated before raising or returning an invalid object.

The supplied proxy transport uses a separate delegated HTTPX transport for each request and its response stream.
The outer transport and provider client still live for the whole app lifespan.
A local CONNECT/TLS test reproduced an [HTTPcore tunnel cleanup problem](https://github.com/encode/httpcore/discussions/921): cancellation during the destination TLS handshake can leave a tunnel active in the shared pool.
Closing only its socket would leave the occupied pool slot, while closing the shared client would interrupt other requests.
Request-owned delegates avoid both problems through the public transport API, and close on response completion, error or cancellation.
The wrapper also retains the current handshake stream through HTTPX's public trace extension, so cancellation before CONNECT can close a socket not yet owned by a completed TLS connection.
This is a deliberate first-version tradeoff: proxied requests do not reuse keep-alive connections and each opens a new CONNECT/TLS session; direct connections are unchanged.
TLS contexts and proxy configuration are created once at startup.

`validate` checks the descriptor and settings without invoking the transport factory, resolving its proxy secret or creating a client.
Imports and custom validators remain trusted Python code and can have side effects.
Offline middleware fixtures keep their in-memory provider and never load the configured provider transport.
The [transport guide](../../provider-transports.md) owns configuration and extension examples.

## Consequences

- **Reliability / Fault Tolerance — [QR-01](../../quality-requirements/qr/QR-01.md):** middleware denial still stops the provider step; a proxy failure uses the provider-error path without a direct fallback or retry in the shipped module.
  The proxy adds an operational dependency, and cancellation remains cooperative.
- **Maintainability / Testability — [QR-02](../../quality-requirements/qr/QR-02.md):** provider formats share one transport interface, and local CONNECT/TLS fixtures can check routing without provider accounts.
  The added descriptor and ownership paths need their own regression checks; these checks do not by themselves establish the full QR scenario.
- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** configuration stores an environment-variable name instead of proxy credentials, and gateway-owned errors avoid exposing raw proxy URLs or authentication values.
  Proxy authentication belongs to the proxy connection; provider credentials travel inside the verified HTTPS tunnel.
- **Trust boundary:** a custom transport is trusted in-process Python that handles provider HTTP requests and credentials.
  It must preserve the no-retry and confidentiality contract; the interface is not a sandbox and cannot prevent arbitrary code from sending other requests or writing its own logs.
- **Scope and operation:** the shipped module supports HTTP and HTTPS proxy endpoints, not SOCKS, per-request proxy rotation or a managed proxy service.
  Proxy changes require restart, and readiness proves local initialization rather than proxy or provider availability.
  Connection setup adds overhead to every proxied request; no latency or capacity claim follows from the local correctness tests.
