# ADR-013: Keep Revocable Browser Sessions In The Gateway

- **Status:** Proposed
- **Created:** 2026-11-23
- **Updated:** 2026-11-23
- **Containers:** `gateway`
- **Addresses:** [FR-023](../../functional-requirements/fr/FR-023.md), [FR-031](../../functional-requirements/fr/FR-031.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-06](../../quality-requirements/qr/QR-06.md)

## Context

The repository owner's [task #335](https://github.com/iteam7/gateway7/issues/335) requests a clearer administration workspace and password accounts that remain signed in across page reloads.
Named operator roles and versioned administrative changes already run inside the gateway.
Adding another identity directory would duplicate those boundaries.
This record describes the implementation proposal; it does not claim a team meeting or Customer acceptance.

## Considered Options

- **Server-side browser sessions for existing named operators.**
  Reuse the durable management store and role checks while keeping browser credentials outside JavaScript storage.
- **Persist operator bearer tokens in browser storage.**
  This makes reload convenient but leaves the reusable administrative credential accessible to scripts and provides no independent browser-session revocation.
- **Introduce an external identity provider.**
  This adds deployment dependencies beyond the requested self-hosted administration workflow.

## Decision Outcome

Chosen option: server-side browser sessions for existing named operators.
An operator's existing identifier is the login name; password accounts retain the same administrator or viewer authorization model.
Passwords use a salted, bounded-cost password derivation function, with bounded verification work and login throttling.
Only password-verification records are stored, and neither passwords nor session credentials enter public snapshots, audit differences or request logs.

A successful password login issues an opaque browser credential in an HttpOnly, SameSite cookie scoped to the operator interface.
The durable store retains its digest, expiry and operator binding so a page reload or ordinary gateway restart does not require another login.
The normal lifetime is twelve hours; the explicit remember option permits seven days.
Secure cookies are the default; a documented explicit override supports loopback development.
Logout, expiry, operator revocation and password reset invalidate the relevant session, and current operator roles remain authoritative for every protected action.
Cookie mutations require the existing operator marker and an additional session-bound CSRF proof, with origin checks at the HTTP boundary.
Explicit bearer authentication remains available for recovery and automation; a malformed supplied bearer never silently falls back to a cookie.
Logical backup restoration does not restore active browser sessions.

The browser workspace uses functional navigation over the existing administration APIs.
It keeps login state in the HttpOnly cookie and short-lived CSRF state in memory, preserves explicit bearer recovery and one-time credential display, and provides responsive navigation without adding another application container.

## Consequences

- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** session credentials are independently revocable and unavailable to JavaScript, while CSRF, current-role checks and safe projections remain required.
  The server now owns password verification and session expiry, and its recovery credential still requires secure deployment handling.
- **Reliability / Fault Tolerance — [QR-01](../../quality-requirements/qr/QR-01.md):** durable sessions survive ordinary restarts, and an unavailable management store fails closed.
- **Interaction Capability / Learnability — [QR-06](../../quality-requirements/qr/QR-06.md):** an operator can sign in and find a functional workspace without copying a bearer credential after each page reload.
- **Operational cost:** browser sessions add private durable state and bounded cleanup work; password recovery remains an authenticated administrative operation rather than a public account-recovery service.
