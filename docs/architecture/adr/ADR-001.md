# ADR-001: Run one Python gateway with separate monitoring applications

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `gateway`, `prometheus`, `grafana`
- **Addresses:** [FR-001](../../functional-requirements/fr/FR-001.md), [FR-003](../../functional-requirements/fr/FR-003.md), [FR-009](../../functional-requirements/fr/FR-009.md), [FR-010](../../functional-requirements/fr/FR-010.md), [QR-02](../../quality-requirements/qr/QR-02.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

Gateway7 is a company-plugin host operated by a small course team, with one configured upstream provider and restart-based installation.
The product's [constraints](../../product-vision.md#constraints) limit operational complexity, and [DEC-011](../../decisions.md#dec-011) permits a deterministic initial demonstration without establishing real-provider acceptance.
The implementation origin is recorded in [DEC-013](../../decisions.md#dec-013); the complete pilot was reviewed and merged in [PR #90](https://github.com/iteam7/gateway7/pull/90).
This record compares the implemented choice with options that could replace it; it does not assert that an earlier meeting evaluated all of them.

The deployed stack is visible in [Compose](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/compose.yaml), the [runtime dependencies](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/pyproject.toml) and the [CLI lifecycle](https://github.com/iteam7/gateway7/blob/0d3d90711abd489046f1c74cd8c8451fbd4aa2fa/gateway7/cli.py).
It has three deployed applications, even though only the gateway is on the chat request path.
The gateway's server-held-key behavior and installed-module extension boundary are specified by [FR-001](../../functional-requirements/fr/FR-001.md) and [FR-003](../../functional-requirements/fr/FR-003.md); [FR-009](../../functional-requirements/fr/FR-009.md) and [FR-010](../../functional-requirements/fr/FR-010.md) assign observation, collection and display to the three applications.

## Considered Options

- **One Python gateway, with separate Prometheus and Grafana applications.** Keep policy execution and provider transport in one application while using existing monitoring services for samples and dashboards.
- **A gateway plus independently deployed plugin services.** Each plugin could have its own process boundary, but the operator would need more services, transport contracts and failure coordination for the same request/response chain; the current trusted-module scope does not require that deployment model.
- **A gateway with a custom monitoring store and dashboard.** This would combine fewer deployed applications with more project-owned persistence, querying and UI work; the team would be responsible for capabilities already provided by the selected monitoring applications.
- **A gateway without monitoring companions.** This is supported by the standalone CLI, but does not provide the shipped dashboard or retained metric history used for operational inspection.

## Decision Outcome

Chosen option: one Python gateway, with separate Prometheus and Grafana applications.
Python hosts the installed middleware packages and their synthetic test harness using the same package contracts, without a service protocol between policies.
FastAPI/Uvicorn serves the async HTTP boundary, Pydantic validates its payloads and configuration, and HTTPX supplies direct provider transport with gateway-owned timeout and error handling.
Prometheus supplies collection, retained time series and queries, while Grafana supplies the provisioned view, avoiding a project-owned monitoring database and UI.
The choice preserves a direct request path and keeps the gateway free of a conversation database or a custom monitoring database.
The [container view](../README.md#container-view) is the maintained set of applications and their state ownership.

Compose starts all three applications; they are not optional profiles in that file.
The CLI can run the gateway alone.
In demo mode, the gateway CLI owns a second, synthetic Uvicorn process inside its Docker container and communicates with it over loopback HTTP; the live override does not start that fixture.
The configured provider adapter is OpenAI, Claude or Gemini, one per gateway process, with no automatic cross-provider routing.

This choice was put in force by the merge of PR #90 on 25 October 2026 after [DeniBorsh's implementation review](https://github.com/iteam7/gateway7/pull/90#pullrequestreview-5643522171).
Accepted records that implemented choice; it does not imply that this later ADR text received the same review or that every linked requirement has passed its checks.

## Consequences

- **Maintainability / Testability — [QR-02](../../quality-requirements/qr/QR-02.md):** the shared Python package contracts and a synthetic upstream let the critical gateway modules be checked without a provider account; the standalone checks do not need the monitoring stack.
  This supports the scenario, while its five-minute and deliberate-fault response measures require their own evidence.
- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** monitoring receives numeric observations rather than message bodies or credentials, and the configured service uses safe gateway-owned error and log output.
  The requirement still needs its synthetic-string search across captured output; an anonymous local dashboard and a demo that prints its public fixture token are not a credentialed shared-deployment boundary.
- **Operational cost:** the full stack has three applications and two data volumes to configure and maintain; gateway liveness does not prove that scraping or the dashboard is healthy.
- **Failure boundary:** plugin code shares the gateway process, so separating monitoring does not isolate faulty or blocking plugins.
- **Data boundary:** the gateway owns transient request state and in-memory counters; monitoring volumes retain numeric samples and application state, not a durable per-request billing history.
- **Local deployment boundary:** published ports bind to loopback and the dashboard is a read-only anonymous local view; shared deployment needs separate transport and operational-access controls.
