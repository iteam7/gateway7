# ADR-014: Activate Typed Policies Through Existing Middleware

- **Status:** Proposed
- **Created:** 2026-11-23
- **Updated:** 2026-11-23
- **Containers:** `gateway`
- **Addresses:** [FR-003](../../functional-requirements/fr/FR-003.md), [FR-018](../../functional-requirements/fr/FR-018.md), [FR-032](../../functional-requirements/fr/FR-032.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-06](../../quality-requirements/qr/QR-06.md)

## Context

The repository owner's [task #335](https://github.com/iteam7/gateway7/issues/335) requests policy creation in the administration workspace without writing plugin code.
The gateway already implements guarded literal text policies, email and phone masking, native Responses hooks and per-client middleware chains.
A second interpreter would duplicate those delivery and protected-payload rules.
This record describes the implementation proposal; it does not claim a team meeting or Customer acceptance.

## Considered Options

- **A fixed declarative registry backed by existing middleware.**
  Typed forms configure the shipped policies and publish ordinary pipeline instances.
- **Accept Python or arbitrary regular expressions in the console.**
  This changes a policy form into a code-execution interface and bypasses the reviewed package-authoring workflow.
- **Implement a separate policy language and execution service.**
  This duplicates current hook semantics and adds deployment and compatibility work beyond the requested workflow.
- **Continue requiring a package for every text policy.**
  This retains unnecessary authoring and installation steps for behavior already implemented by the gateway.

## Decision Outcome

Chosen option: a fixed declarative registry backed by existing middleware.
The builder accepts only typed data for literal guard, literal redaction, email masking and phone masking templates.
It selects request, response or both phases and bounded settings appropriate to that template.
Preview uses the same pure transformation as the runtime and does not call a provider or persist the submitted text.
Native and structured-payload guards remain the existing middleware contract; a text preview is not a certification of every delivery profile.

Definitions and ordered global or per-client assignments live in the versioned control document.
Startup validates and restores definitions before resolving stored middleware references.
An administrative mutation validates a complete candidate, checks the shared revision and current actor, commits the control and audit changes, then publishes the candidate on the event loop.
Configured plugins and required middleware remain present.
Hot changes reuse existing external plugin instances and create only the selected trusted, immutable template instances.
Already-admitted requests retain their captured pipeline, while subsequent requests observe the new assignment.
Response-dependent policies retain the established early-delivery refusal instead of silently skipping response inspection.
Malformed persisted definitions fail startup rather than silently dropping the corresponding policy.

## Consequences

- **Reliability / Fault Tolerance — [QR-01](../../quality-requirements/qr/QR-01.md):** policy definitions and assignments survive restart, while publication must preserve in-flight snapshots and unknown-usage accounting.
- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** forms cannot import arbitrary modules or execute submitted code, and policy audit entries describe changes without copying preview text or literal terms into logs.
  Existing protected-field and consent guards still apply to the selected middleware.
- **Interaction Capability / Learnability — [QR-06](../../quality-requirements/qr/QR-06.md):** an operator can create and activate supported policies through forms.
  A new behavior beyond the bounded registry still requires the established Python authoring workflow.
