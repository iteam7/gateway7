# QR-01: Refuse Forwarding After A Request-Side Middleware Failure

When a request-side middleware raises, denies or overruns its time budget, the provider receives no call for that request on any supported operating system.

- **Status:** Active
- **Characteristic:** Reliability
- **Sub-characteristic:** Fault Tolerance
- **Business importance:** High
- **Technical risk:** High

## Scenario

### Source

A trusted company middleware configured in the gateway's middleware list.

### Stimulus

During request processing the middleware raises an exception, returns a denial, or exceeds its own-work time budget, including a middleware that catches the cancellation and returns a result afterwards.

### Environment

The gateway runs on Windows or Linux with one configured provider, per [`CON-01`](../../product-vision.md#con-01), and the request is otherwise valid and authorized.

### Artifact

The middleware runner in `gateway7/pipeline.py` and the provider invocation it guards.

### Response

The gateway shall stop processing the request, return its safe error to the client, and make no provider call.

### Response Measure

Across 50 consecutive runs of each failure case on both Windows and Linux, the recording upstream records zero requests and every client response is the safe error with HTTP status 403, 500 or 504.

## QRT-01

Fifty requests for each request-side middleware failure reach the recording upstream zero times and each returns the safe error, on Windows and on Linux.

- **Status:** Active
- **Level:** CI
- **Runs at:** the `Exercise all four synthetic scenarios 50 times` step of the `fault-tolerance` job in `.github/workflows/quality-requirements.yml`, on native Windows and Linux runners for every pull request and on `main`.

### Procedure

1. Let the `Quality requirements` workflow run on `main`.
2. Open both `Fault tolerance (ubuntu-latest)` and `Fault tolerance (windows-2022)` jobs.
   The jobs check out the same commit and install the locked dependencies on Python 3.12.
3. In `Record checkout and runtime`, read the actual source commit, operating system and Python version.
4. In `Exercise all four synthetic scenarios 50 times`, read the output of `uv run --locked python -m demo.fault_tolerance --runs 50` on each runner.
   It starts the recording upstream and one gateway per failure case: a middleware that raises, one that denies, one that overruns its own-work budget, and one that catches the cancellation and continues after the budget.
5. Read the `upstream requests` count, HTTP status and safe error code on every case line in both jobs.
   The step preserves the harness exit code, so a failing run fails its job.

**Pass when:** on both Windows and Linux, every case line reports `upstream requests=0` with all 50 responses HTTP 403, 500 or 504 carrying that case's safe error code, and the command exits 0.
