# QR-05: Find A Failed Request From The Staging Signals

Within five seconds of a failed chat request, an operator finds its log point by request identifier in the staging observability organization, and within one minute the SLI-01 query shows the failure series.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

The operator of the staging deployment, investigating a failure a client reported with the request identifier from its error response.

### Stimulus

A chat request in the core task fails at the gateway: an authenticated client asks for a model it is not allowed to use.

### Environment

The staging deployment on the university VM, with telemetry collection enabled and the observability pipeline exporting to the staging OpenObserve organization.

### Artifact

The gateway's request path and the signals it emits for [SLI-01](../../observability.md#sli-01): the per-request log point and the request-duration histogram.

### Response

The staging organization returns the failed request's log point with its request identifier, route and failure labels, and the SLI-01 aggregate carries a separate failure series.

### Response Measure

Within five seconds of the failed request's response, a query of the staging organization by its request identifier returns one log point carrying the identifier, the route and the failure label; within one minute, the SLI-01 query returns the failure series with a numeric five-minute P95.

## QRT-01

A failed chat request against staging is found in the staging organization by its request identifier within five seconds, and the SLI-01 query shows its failure series with a P95 within one minute.

- **Status:** Active
- **Level:** deployed
- **Runs at:** the staging deployment on the university VM, from a machine on the university network: `uv run --locked python scripts/check_sli.py --org staging --confirm-staging --commit "$DEPLOYED_COMMIT"`, using `$STAGING_URL`, `$OPENOBSERVE_URL` and [SLI-01](../../observability.md#sli-01).

### Procedure

1. Deploy the full commit under test to staging by following [deployment](../../deployment.md#manual-deployment), with telemetry collection enabled for `staging` as in [the telemetry pipelines](../../deployment.md#telemetry-pipelines).
   On the VM, verify that the selected gateway stack and its OpenObserve organization are staging, and set `DEPLOYED_COMMIT` to that deployment's full lowercase SHA.
   The command records the target and commit as operator assertions; it cannot independently attest a remote stack or commit.
2. Set `STAGING_URL` and `OPENOBSERVE_URL` to the gateway's and OpenObserve's base HTTP(S) addresses, without user information, paths, queries or fragments.
   Set `GATEWAY7_ENVIRONMENT=staging`, `GATEWAY7_CLIENT_TOKEN` to a restricted staging client token, and `OPENOBSERVE_USER` and `OPENOBSERVE_TOKEN` to a query credential for the staging organization, without printing any of them.
   When analytics collection is enabled, follow the deployment runbook to mark this check's traffic as `source=smoke` in staging, and restore the normal traffic source afterwards.
   Do not use production: this test deliberately generates a failure and queries only the staging organization.
3. Run `uv run --locked python scripts/check_sli.py --org staging --confirm-staging --commit "$DEPLOYED_COMMIT"`.
   The script checks readiness, verifies that unauthenticated model listing fails and authenticated listing returns an allowlist, and checks that the test's model is absent from that list.
   It reads the failure histogram's baseline count, then requests that forbidden model on `/v1/chat/completions`, which must return HTTP 403 `model_forbidden` before a provider call.
   It sends no successful chat requests and needs no paid provider call; the retained `--successes` compatibility option accepts only `0`.
4. Read the result: the script queries `gateway7_requests` by the response's generated `X-Request-ID`, checking the identifier, route `openai_chat`, outcome `client_error`, status 403, error code and finite nonnegative duration.
   The five-second query deadline starts at the failed response, and a slow query cannot extend it.
   Then it requires a new histogram observation and runs the exact [SLI-01](../../observability.md#sli-01) P95 query, with a one-minute deadline measured from the same response.
   The output records only fixed labels, the request identifier, measured times, the P95 and the operator-supplied commit; no address, credential or raw backend response is printed.
5. Open the staging dashboard's `SLI-01 API request P95 by outcome` chart and capture a sanitized screenshot showing the failure series.
   Record the staging environment, verified deployed commit, command, exit code, safe result fields and screenshot in the current week's evidence, and link the result from the testing plan.
   Protocol tests or a local backend run are development validation and do not establish a deployed staging result.

**Pass when:** the command exits 0 and prints `PASS QR-05 QRT-01`, its matching log point is queryable within 5 seconds of the response, and its `openai_chat` / `client_error` series has a finite nonnegative five-minute P95 within 60 seconds of that response after a new histogram observation, with the staging chart showing that failure series.

The extra histogram-count check prevents an old P95 series alone from satisfying the test.
Run on quiet staging traffic: expiry of older observations from the five-minute window can conservatively fail the count-increase check, in which case investigate and rerun rather than extending the deadlines.
Addresses and credentials remain in the private submission.
The protocol uses OpenObserve's [log search API](https://openobserve.ai/docs/reference/api/search/search/) and [Prometheus-compatible metrics API](https://api.openobserve.ai/swagger/).
