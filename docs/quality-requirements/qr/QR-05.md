# QR-05: Find A Failed Request From The Staging Signals

Within five seconds of a failed chat request, an operator finds its log point by request identifier in the staging observability organization, and within one minute the SLI-01 query shows the failure series.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

The operator of the staging deployment, investigating a failure a client reported with the request identifier from its error response.

### Stimulus

A chat request in the core task fails at the gateway: an authenticated client asks for a model it is not allowed to use.

### Environment

The staging deployment on the university VM, with telemetry collection enabled and the observability pipeline exporting to the staging OpenObserve organization.

### Artifact

The gateway's request path and the signals it emits for [SLI-01](../../observability.md#sli-01): the per-request log point and the request-duration histogram.

### Response

The staging organization returns the failed request's log point with its request identifier, route and failure labels, and the SLI-01 aggregate carries a separate failure series.

### Response Measure

Within five seconds of the failed request's response, a query of the staging organization by its request identifier returns one log point carrying the identifier, the route and the failure label; within one minute, the SLI-01 query returns the failure series with a numeric five-minute P95.

## QRT-01

A failed chat request against staging is found in the staging organization by its request identifier within five seconds, and the SLI-01 query shows its failure series with a P95 within one minute.

- **Status:** Active
- **Level:** deployed
- **Runs at:** the staging deployment on the university VM, from a machine on the university network: `python3 scripts/check_sli.py --gateway $STAGING_URL --observe $OPENOBSERVE_URL --org staging`, reading [SLI-01](../../observability.md#sli-01).

### Procedure

1. Deploy the commit under test to staging by following [deployment](../../deployment.md#manual-deployment), with telemetry collection enabled for `staging` as in [the telemetry pipelines](../../deployment.md#telemetry-pipelines).
2. On a machine on the university network, set `STAGING_URL` and `OPENOBSERVE_URL`, set `GATEWAY7_CLIENT_TOKEN` to a staging client token, and set `OPENOBSERVE_USER` and `OPENOBSERVE_TOKEN` to a query credential for the staging organization, without printing any of them.
3. Run `python3 scripts/check_sli.py --gateway $STAGING_URL --observe $OPENOBSERVE_URL --org staging --commit <deployed commit>`.
   The script lists the client's allowed models, sends two successful chat requests in the core task, and then sends one chat request for a model the client may not use, which fails with HTTP 403 `model_forbidden`.
   It queries the staging organization's log stream by the failed request's `X-Request-ID` until the point appears or five seconds pass, and prints the point.
   It then runs the SLI-01 query against the same organization until the `openai_chat` / `client_error` series has a numeric value or one minute passes, and prints the series and its P95.
4. Open the staging dashboard's `SLI-01 API request P95 by outcome` chart and capture a sanitized screenshot that shows the failure series.
5. Record the staging environment, the commit, the script's output and the screenshot as the evidence; name no address.

**Pass when:** the log point for the failed request is returned within 5 seconds of its response with its `request_id`, route `openai_chat`, outcome `client_error` and error code `model_forbidden`, the SLI-01 query returns the `openai_chat` / `client_error` series with a numeric P95 within 1 minute of that response, and the command prints `PASS QR-05 QRT-01` and exits 0.
