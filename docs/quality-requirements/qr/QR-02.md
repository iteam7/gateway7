# QR-02: Catch A Broken Gateway Change Without A Provider Account

A developer runs the checks covering the gateway's critical modules from a clean checkout without any provider account, and a change that breaks their contract fails those checks.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Testability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A team member or instructor reviewing a change to the gateway.

### Stimulus

The change alters the behavior of a critical module: the middleware runner `gateway7/pipeline.py`, the HTTP entry point `gateway7/app.py`, client authentication `gateway7/auth.py`, or the provider adapters `gateway7/providers.py`.

### Environment

A clean checkout with only the locked dependencies installed by following `docs/setup.md`, no provider API key, and no network access to any LLM provider.

### Artifact

The automated test suite under `tests/` and the one-command demonstration `demo/run.py`.

### Response

The checks shall run to completion offline and shall report a failure for a change that breaks the critical modules' documented behavior.

### Response Measure

`uv run --locked pytest` and `uv run --locked python -m demo.run` complete within 5 minutes and exit 0 on unchanged `main`, and each exits non-zero when the request-side failure handling in `gateway7/pipeline.py` is changed to forward the request anyway.

## QRT-01

The product CI runs the suite and the demonstration from a clean checkout without provider credentials, and both fail when request-side failure handling forwards the request anyway.

- **Status:** Active
- **Level:** CI
- **Runs at:** the `Run tests` and `Exercise separate HTTP processes` steps of the `check` job in `.github/workflows/python.yml`, on every pull request and on `main`.

### Procedure

1. Let the `check` job of the Python checks workflow run on `main`; it starts from a fresh checkout and installs only the locked dependencies, with no provider key.
2. In the `Run tests` step, read the results of `tests/test_testability.py`: `test_each_critical_module_has_a_test` finds a test importing each of `gateway7/pipeline.py`, `gateway7/app.py`, `gateway7/auth.py` and `gateway7/providers.py`, and `test_forwarding_after_request_failure_fails_the_suite_and_the_demo` copies the checkout, changes `gateway7/pipeline.py` to forward the request after a middleware raises or denies, and runs `pytest` and `python -m demo.run` on the copy.
3. Read the result and the duration of the `Run tests` and `Exercise separate HTTP processes` steps.

**Pass when:** on `main`, both steps succeed and each finishes within 5 minutes, with both `tests/test_testability.py` tests passing, which shows the unchanged suite and demonstration exit 0 and the copy with forwarding makes each exit non-zero.
