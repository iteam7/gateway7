# FR-032: Create And Activate Declarative Policies In The Console

- **Status:** Active
- **Traces to:** [Repository owner task #335](https://github.com/iteam7/gateway7/issues/335), [FR-003](FR-003.md), [FR-018](FR-018.md), [ADR-014](../../architecture/adr/ADR-014.md)
- **Containers:** `gateway`

## Behavior

When an administrator creates a policy through the console, the gateway shall accept only the supported literal guard, literal redaction, email masking and phone masking templates with validated text settings and request, response or both phases.
The policy editor shall accept no Python code, regular expression or module import path.
When an administrator activates policies globally or for selected clients, the gateway shall publish their validated order for subsequent requests while retaining the configured global and client middleware baseline.
Managed definitions and assignments shall persist across gateway restarts.
The gateway shall apply activated policies through its actual Chat and native Responses pipelines, preserving protected structured fields and source usage.
The gateway shall permit an administrator to preview a proposed policy against bounded plain text without contacting a provider or saving that text.

## Acceptance Criteria

### AC-01

Given an administrator using the policy builder, when each supported template is selected, then a valid definition can be saved and listed without installing code or editing YAML.
Unknown templates, code/module fields, invalid phases, duplicate or oversized literal terms, unsupported fields and invalid replacements are rejected without changing state.
A viewer cannot create, update, delete, preview or activate a policy.

### AC-02

Given configured required middleware, when managed policies are assigned, reordered or removed, then the configured middleware remains active and retains its order.
Managed global policies follow the configured global chain, and managed client policies follow that client's configured additions.
Duplicate assignments and a policy assigned both globally and to the same client are rejected.
An assigned definition cannot be deleted until its assignments are removed.

### AC-03

Given an activated literal request guard and a matching synthetic request, then the request is denied before a provider call.
Given activated redaction or masking and synthetic matching text in its selected phase, then the permitted text changes while provider usage and protected call/item identities are retained.
Matches in protected executable fields are denied rather than rewritten.
The same configured policy applies to the supported Chat and native Responses paths.

### AC-04

Given request-only managed policies and compatible configured middleware, early delivery can use their request preparation hooks.
A reached response-dependent policy refuses early delivery before provider work, while an earlier request denial retains its precedence.
Disabling or removing the configured privacy baseline is not an early-delivery workaround.

### AC-05

Given a preview request, the result reports matching, redaction or denial for the supplied plain text and zero provider calls; it does not claim coverage of history, tools, native structures or a complete pipeline.
The preview text is not saved in state, audit history or logs.

### AC-06

Given a successful policy mutation, then the global management revision advances with its attributable sanitized audit event.
A stale revision cannot overwrite another operator's policy change.
After restart, the same definitions and assignment order are restored; invalid stored definitions prevent ready operation rather than silently removing a policy.
