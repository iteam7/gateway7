# FR-017: Limit Each Client's Request Rate

- **Status:** Active
- **Traces to:** [US-07](https://github.com/iteam7/gateway7/issues/36), operator rate extension in [task #240](https://github.com/iteam7/gateway7/issues/240), [FR-006](FR-006.md), [ADR-003](../../architecture/adr/ADR-003.md)
- **Containers:** `gateway`

## Behavior

When an operator configures a client's requests-per-minute quota, the gateway shall share one initially full request-token bucket for that client across native chat, Chat Completions and Responses, including buffered and early delivery.

The gateway shall refill that bucket continuously using monotonic time at the configured rate, up to the configured capacity, and shall debit one request token only after authentication, payload/model validation and concurrency admission succeed.

When the bucket has no whole request token available, the gateway shall reject the request with HTTP 429, code `rate_limited` and a bounded integer `Retry-After` for the rounded-up wait until one token is available, before middleware or a provider call.

The gateway shall refund a debited token when operation/task creation rolls back admission, while retaining the charge for later policy, capability or provider failures of an admitted request.

The gateway shall keep bucket state local to one process and reset it on restart; an absent quota shall preserve existing authenticated and anonymous synthetic-demo behavior.

## Acceptance Criteria

### AC-01

Given a client's quota of two requests per minute and a full bucket, when it completes one native chat and one Chat Completions request without refill, then a subsequent Responses request receives HTTP 429 with `rate_limited`, `Retry-After: 30` and no third provider call.

### AC-02

Given a quota of one request per minute and an exhausted bucket, when a controlled monotonic clock advances by 30 seconds, then the request remains rejected with `Retry-After: 30`; after 60 seconds it succeeds.
A second configured client's bucket remains independent.

### AC-03

Given a full bucket, requests rejected for authentication, payload/model validation or concurrency capacity consume no token.
Operation/task-creation failure refunds its debit, while an admitted provider failure consumes one token and can exhaust the bucket.

### AC-04

Given no configured rate, existing requests remain unrestricted by a client rate quota.
Given separate gateway applications or a restarted process, each begins with independent full buckets; no hard model-token, cost or distributed-budget guarantee is established.
