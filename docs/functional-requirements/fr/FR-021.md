# FR-021: Manage Client Accounts In The Operator Console

- **Status:** Active
- **Traces to:** [Repository owner request, 2026-11-15](https://github.com/iteam7/gateway7/issues/288), [Repository owner task #295](https://github.com/iteam7/gateway7/issues/295), [US-07](https://github.com/iteam7/gateway7/issues/36), [FR-006](FR-006.md), [FR-020](FR-020.md), [ADR-008](../../architecture/adr/ADR-008.md), [ADR-009](../../architecture/adr/ADR-009.md), [ADR-010](../../architecture/adr/ADR-010.md)
- **Containers:** `gateway`
- **Changed:** 2026-11-16: The repository owner selected PostgreSQL as the primary managed backend, retaining explicit local SQLite compatibility.

## Behavior

When durable management is configured, the gateway shall let the authenticated operator create, edit, suspend, enable and delete client accounts through the browser console.
An editable account shall carry its stable identity, enabled state, model restriction, concurrent-request limit, request-rate limit, ordered additional middleware selection, owner label, tags and optional permitted default model.
Account inspection shall distinguish configured and effective model permissions.

When the operator creates an account or issues a replacement credential, the gateway shall return a generated client token once and shall retain only its digest.
When the operator rotates, revokes or deletes a credential, the gateway shall reject the former credential on subsequent protected client requests.
Enabling an account without a credential shall not restore an earlier token.
A client shall support separately named keys with creation time, expiration, last-use metadata and independent revocation or rotation.
Newly issued keys shall have a finite default lifetime; expired keys shall not authenticate, and removing one key shall not disable the user's other valid keys.
Account and key writes shall require the current administrative revision and atomically record the safe audit entry described by [FR-027](FR-027.md).

When the operator saves a valid account change, the gateway shall persist it and apply it to subsequent requests without a restart.
The gateway shall retain each already-admitted request's existing policy chain and admission lease until its normal completion and cleanup.
A change shall not remove global middleware, select an unknown or disabled middleware, broaden the provider-wide model restriction, or reset unrelated admission state.
Invalid edits shall leave the effective and stored account unchanged.

When durable management starts with an uninitialized store, the gateway shall import configured seed accounts once, or allow the operator to create the first account when no seeds exist.
On later starts, the stored accounts and credential digests shall remain authoritative, without requiring seed client token environment values or restoring credentials from edited seed configuration.
The gateway shall retain deleted accounts' aggregate usage and reserve their identities against reuse.

The gateway shall require the separate operator bearer credential and an explicit operator request header for account mutations, and shall reject cross-origin mutation requests.
The console shall not store credentials in cookies, URLs or browser storage, and shall clear displayed account data and one-time tokens when disconnected.

The gateway shall require private persistent storage for managed account state and shall reject another gateway process opening the same store concurrently.
The gateway shall validate versioned managed state at startup and reject an incompatible or unavailable selected store instead of resetting it or falling back to another backend.
When the managed database connection is lost, the gateway shall stop forwarding client requests and report itself as not ready until restarted with a healthy connection.
Without durable management configuration, existing account configuration and the read-only console shall retain their prior behavior.

## Acceptance Criteria

### AC-01

Given operator access with durable management and no seeded clients, when the operator creates a synthetic client in the console, then the console shows the generated token once and the client can authenticate with its selected models.
Later state reads and the stored database contain no recoverable raw token.

### AC-02

Given a managed client, when the operator edits model permissions, capacity, request rate or additional middleware, then subsequent native chat, Chat Completions and Responses requests use the saved profile, including supported streaming modes.
The global middleware baseline remains present, provider-wide restrictions remain effective, and invalid selections or limits change neither stored nor live state.

### AC-03

Given an account with a token, when the operator suspends the account, rotates or revokes its token, or deletes the account, then the former token cannot start another protected client request.
An already-admitted request retains its original middleware chain and completes cleanup without releasing another request's capacity.
Re-enabling a revoked account does not make its former token valid.

### AC-04

Given accounts created, edited, revoked and deleted in the console, when the gateway restarts on the same store without seed client token variables, then the saved profiles and revocations remain effective, deleted IDs cannot be recreated, and historical usage remains available.
Starting another gateway process against the same store fails without exposing credential values or private paths.

### AC-05

Given missing, client, provider, duplicated, cookie or query credentials, a missing operator request header, or a cross-origin request, when a caller attempts an account mutation, then it cannot change stored or live account state.
Unauthenticated requests fail before their bodies are read; operator responses prohibit caching.
Given management is absent, account mutation endpoints cannot modify legacy configured clients.

### AC-06

Given a browser session, when an operator creates and edits an account, issues and revokes a token, changes access and reads a filtered usage report, then the rendered controls perform those operations and show failures without exposing secrets.
Disconnect clears the credential, one-time token and account data; stale in-flight responses cannot restore a disconnected session.

### AC-07

Given PostgreSQL-backed management, when the gateway restarts or its container is recreated while retaining the database volume, then managed profiles, credential digests, deleted identities and usage remain unchanged.
An unknown schema version, malformed stored state, unavailable database or second gateway owner prevents readiness and client forwarding without exposing connection details.
After a database connection is lost, the running gateway returns a service-unavailable response for new protected client requests and readiness checks until restarted with a healthy database.
