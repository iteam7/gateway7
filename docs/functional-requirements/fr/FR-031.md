# FR-031: Sign In To The Operator Console With A Password

- **Status:** Active
- **Traces to:** [Repository owner task #335](https://github.com/iteam7/gateway7/issues/335), [ADR-013](../../architecture/adr/ADR-013.md)
- **Containers:** `gateway`

## Behavior

When an administrator provisions a named operator with a password, the gateway shall allow that operator to sign in using the operator ID as the username and the supplied password.
The gateway shall expose no public account-registration path and shall retain the server-managed bootstrap credential for administrative recovery.
When password sign-in succeeds, the gateway shall authenticate later console requests through a private browser cookie until the session or operator expires or access is revoked.
The console shall restore a valid session after a page refresh without requiring an operator token to be pasted again.
The gateway shall apply the operator's current role, browser-origin checks, write marker, session CSRF proof and configuration revision checks to protected operations.
When an operator signs out, its session shall stop authenticating subsequent requests.
When an administrator resets an operator's password, changes its role or revokes that operator, all of that operator's browser sessions shall stop authenticating subsequent requests.
Passwords and raw session credentials shall not appear in state projections, logs or audit records.

## Acceptance Criteria

### AC-01

Given a managed installation with no password account, when the bootstrap administrator connects through the console's recovery-token option and creates an operator with a username, display name, role and password, then that operator can sign in through the password form without receiving or pasting a bearer credential.
An unauthenticated caller cannot create an account.

### AC-02

Given a successful ordinary sign-in, the server issues an HttpOnly, SameSite=Strict cookie scoped to `/operator`, with the configured absolute session lifetime, 12 hours by default.
Given an explicit remembered sign-in, its persistent cookie and server expiry last at most the configured seven-day default.
Neither session outlives the named operator's expiration.
The default cookie is Secure; an explicit insecure local-development setting permits HTTP only for a loopback request host and actual loopback peer.

### AC-03

Given an unexpired session and unchanged durable management state, when the browser refreshes or the gateway process restarts, then the console can resume that session without a new password.
After logout, password reset, role change, operator revocation or expiry, the previous session is rejected.
Rotating only an automation bearer does not revoke an independent password session.
A logical backup restore does not restore authenticated browser sessions.

### AC-04

Given a password-authenticated viewer, when a protected mutation is attempted, then it is denied without changing state.
Given a session-authenticated administrator, when a mutation omits the session CSRF token, uses another origin or carries a stale revision, then it is rejected without changing state.
A role or access change that occurs while a write request waits is enforced before committing that write.

### AC-05

Given malformed, unknown-account or incorrect-password sign-in attempts, then authentication fails without revealing whether the username exists or exposing supplied secrets.
Password validation and bounded password work prevent unbounded authentication work from blocking ordinary HTTP processing.
A new or reset password must contain 12–128 characters and at most 512 UTF-8 bytes.
