# FR-013: Exchange guarded function-tool turns

- **Status:** Active
- **Traces to:** [US-01](https://github.com/iteam7/gateway7/issues/30), [US-05](https://github.com/iteam7/gateway7/issues/34), [ADR-005](../../architecture/adr/ADR-005.md)
- **Containers:** `gateway`
- **Changed:**
  - 2026-11-05: added the separate early Chat delivery contract explicitly requested by the user, while retaining the buffered default and its existing criterion identifiers; this is not a Customer acceptance record.
  - 2026-11-05: added the explicitly user-requested native Responses HTTP subset and separate consent boundaries; independent review and live harness verification remain separate from this requirement, with no new Customer or team decision asserted.
  - 2026-11-05: replaced the temporary native-early guard with the implemented typed leading-prefix contract; component reviews do not establish production, end-to-end or container/live acceptance.

## Behavior

When an authorized client supplies a supported function definition and asks the configured OpenAI provider to complete an agent turn, the gateway shall preserve the function definition, tool-choice controls and matching call/result identifiers through its provider exchange.

When the provider returns a supported function call, the gateway shall check its structure, advertised function and configured response policies before delivering that call to the client.

When the client returns a tool result with its matching call identifier in the conversation history, the gateway shall forward the validated history for the next turn without executing the tool itself.

When the client requests Chat Completions SSE without explicitly selecting early delivery, the gateway shall collect and validate the provider's streaming answer, run full-response middleware, and then deliver the checked text or function call with its completion reason and terminal marker.

When an authorized client explicitly selects early delivery for an OpenAI streaming request with a compatible request-only chain, the gateway shall complete all configured request checks before invoking the provider and may deliver validated text events before provider completion.

When that early request has an incompatible provider, the gateway shall return HTTP 400 without invoking the provider.
When an active preparation hook refuses its incompatible configuration, the gateway shall return HTTP 400 unless an earlier request hook has already denied with HTTP 403 (`policy_denied`).
Neither outcome invokes the provider, skips a policy or silently selects buffered delivery.

When an early turn contains a function call, the gateway shall withhold its executable payload until complete arguments, call identity, tool choice and provider completion have passed validation.

When an early stream fails after text has been delivered, the gateway shall end it with a safe stream error when delivery remains possible, or close the connection, without a successful completion marker or an unvalidated tool call.
Already delivered text cannot be retracted.

When a client is slow or disconnects during early delivery, the gateway shall retain bounded backpressure, the original request deadline and its occupied pipeline slot until the owning job and cleanup finish.

When the configured provider or middleware chain does not support that agent payload, the gateway shall return a safe error without invoking the provider.

When an authorized client submits a supported native Responses HTTP request, the gateway shall preserve ordered native message, reasoning, function/custom and tool-search items without converting them to Chat Completions or silently discarding unknown fields.

When native parallel or namespaced calls are returned, the gateway shall validate their advertised kind, namespace and name, preserve distinct item/call identities and raw custom input, and require subsequent results to match their preceding call identities and kinds.

Before forwarding a native request, the gateway shall require all active middleware to support native preparation and response checking, preserve the authorized model and independent consent outside middleware-editable payloads, and make at most one provider attempt with storage disabled.

When exact typed encrypted or inline-media content is present, the gateway shall require explicit opaque consent and preserve those values without claiming plaintext inspection, while retaining policy checks on adjacent plaintext and other structured fields.

When provider-hosted web search or server tool search is requested, the gateway shall require separate hosted-tool consent; subsequent response denial shall withhold returned content without claiming to prevent or undo provider-side execution.

For native JSON or default checked SSE, the gateway shall validate the complete provider response and run response checks in reverse configured order before sending client content, retaining native terminal state and only source-reported usage.

When an authorized client explicitly selects native early mode with `stream: true`, OpenAI and compatible request-only native hooks, the gateway shall retain separate immutable consent and native identity/position metadata while limiting early text to an eligible leading assistant prefix.

When any other item/part, held non-text metadata or leading-part closure ends that prefix window, the gateway shall hold later text until strict final validation without rejecting an otherwise supported profile, reindexing items or flattening native data.

When native early delivery includes executable tools, refusal, reasoning or opaque content, the gateway shall withhold those events until strict request-aware terminal validation, without treating a held hosted-tool record as prevention of consented provider-side execution.

After any native prefix is delivered, the gateway shall reconcile final content against its published native identities and text, and on a late failure shall emit a sanitized native failure when possible or abort, without a false completed event or Chat terminal marker.

## Acceptance Criteria

AC-01 through AC-10 retain the Chat Completions contract; AC-11 onward cover the separate native Responses subset.

### AC-01

Given a synthetic OpenAI upstream returning one valid function call across several SSE fragments, when a client requests a default buffered streaming turn advertising that function, then the upstream receives `stream: true` and the client receives one structurally equivalent function call with `finish_reason: tool_calls` and the SSE terminal marker.

### AC-02

Given a valid function call in an assistant history message followed by its tool-result message, when the client requests the next turn, then the provider receives the same call identifier on both messages and the client receives the checked final answer.
An orphaned or duplicate tool result, an unknown function choice and unsupported parallel calls fail before forwarding.

### AC-03

Given a response policy blocking a term in text or decoded tool arguments, when a default buffered turn contains that term across provider stream fragments, then the client receives HTTP 403 with `policy_denied`, receives no assistant content or tool-call event, and exactly one provider invocation is recorded.

### AC-04

Given a provider stream missing a terminal completion reason or terminal marker, or containing malformed function-call arguments, when processing finishes, then the client receives the safe provider error instead of a successful completion or an executable call.
Valid independently reported usage remains observable even when answer validation fails.

### AC-05

Given a tool request with a configured middleware that has not declared tool support, or a streaming/tool request with an unsupported provider adapter, when the request is checked, then it is rejected before provider invocation.
The existing native text-chat path and nonstreaming SDK call remain available.

### AC-06

Given a compatible request-only chain and a synthetic OpenAI provider that pauses after its first nonempty text event, when the client requests `stream: true` with `X-Gateway7-Stream-Mode: early`, then that text reaches the client before the provider is allowed to finish.
The provider receives the request after every configured preparation hook and is invoked at most once.

### AC-07

Given an early request with a missing preparation hook, a nonstreaming request, an unsupported provider, or an invalid/repeated mode header, then the client receives HTTP 400 and the provider call count is zero.
Given present preparation hooks and an active reference policy configured for `response` or `both`, when that policy's hook is reached, then the client receives HTTP 400 and the provider call count is zero.
A request hook that denies first instead returns HTTP 403 with `policy_denied` and zero provider calls, even when a later hook is incompatible.

### AC-08

Given an early stream that has delivered valid text, when later provider data is malformed or lacks its required terminal marker, then the client receives a safe error event or an interrupted stream, with no successful finish, no `data: [DONE]` and no executable tool payload.
The earlier prefix may remain visible; HTTP 200 by itself does not establish completion.

### AC-09

Given a slow or disconnected early client, when a downstream send blocks or cancellation cleanup is still running, then further provider reads do not race ahead through a producer queue and the occupied pipeline slot is not released before its job finishes.
The original overall deadline still bounds generation and downstream sends.

### AC-10

Given a valid early function-tool turn with arguments split across provider events, when text or partial arguments have arrived but provider completion is not yet validated, then no tool-call delta reaches the client.
After successful validation, the client receives the matching call, finish reason, requested usage and terminal marker without execution by the gateway.

### AC-11

Given advertised native namespaced functions and a custom tool, when an authorized native HTTP turn returns ordered parallel calls, then JSON and checked SSE preserve their order, namespaces, distinct item/call IDs and original argument/custom-input strings, with no Chat `choices` conversion.
Matching native tool results in the next request retain their call correlation; orphaned, duplicated or wrong-kind results fail before provider work.

### AC-12

Given native encrypted reasoning or inline media in a request without `X-Gateway7-Allow-Opaque: true`, then the request is rejected with HTTP 400 and zero provider attempts.
With valid explicit opaque consent, the opaque strings remain unchanged, while a blocked adjacent plaintext field still produces `policy_denied` rather than becoming exempt from inspection.
Invalid or duplicate consent headers are rejected before provider work, and middleware cannot grant or alter consent through payload edits.
Unexpected unconsented provider output fails response validation before delivery rather than being released.

### AC-13

Given advertised native web search or server tool search without `X-Gateway7-Allow-Hosted-Tools: true`, then the request is rejected with HTTP 400 and zero provider attempts, even if opaque consent was granted.
With hosted consent, a response-policy denial withholds the returned output but does not establish that provider-side execution was prevented; the provider attempt has already occurred.

### AC-14

Given native payloads containing a policy match in a protected identifier, executable argument/custom input or schema field, when masking or redaction would change that protected value, then the gateway denies rather than rewriting it.
Permitted free-text redaction is consistent across checked deltas, item snapshots and the final native response, while protected identity, usage and terminal metadata remain unchanged.

### AC-15

Given a default native streaming request, when complete validation and reverse response policy succeed, then the client receives native `response.*` events with stable references and a terminal native status, never Chat's `data: [DONE]` marker.
No output-item or executable-call event is delivered before those checks; response-policy denial remains JSON HTTP 403 without earlier SSE content.
An incomplete native response is not relabeled completed, incomplete executable calls are rejected, and partial or unknown usage is not filled with invented zero counts.

### AC-16

Given a native request and an active middleware lacking native preparation or response checking, then the gateway returns HTTP 400 before any middleware hook or provider attempt rather than skipping that middleware.
Explicit native early delivery additionally requires `stream: true`, OpenAI, native early provider capability and `prepare_early_responses` on every active middleware; missing prerequisites reject before provider work.
With hooks present, a reached response-dependent configuration refuses with HTTP 400 unless an earlier request hook has denied with HTTP 403 (`policy_denied`); neither outcome invokes the provider.

### AC-17

Given a valid native early request and a parser-validated leading assistant `output_text` record at output/content indices `0/0`, with supported head metadata and an open prefix window, when it is released before upstream completion, then native events retain the response/item IDs, indices and assistant phase with a consistent monotonic delivery sequence.
Only text and its native start framing are released; executable tools, refusal, reasoning, opaque content and terminal completion remain held for final validation.

### AC-18

Given a native stream with another item/part, held non-text metadata or leading-part closure, then leading-prefix eligibility closes permanently and later text waits for final validation.
An otherwise supported reasoning/tool/refusal-first, interleaved or multiple-message profile still retains its full canonical output, item order, IDs, phases and indices, without an all-profile first-token latency guarantee.
The explicit early mode remains request-only during holdback; it does not silently regain the buffered response-policy chain.

### AC-19

Given a native early stream that has published a prefix, when later data or final reconciliation fails, then the client receives a sanitized native `response.failed` when delivery remains possible, or an aborted stream, without false `response.completed`, Chat `data: [DONE]` or held executable output.
The same app lifecycle retains backpressure, original deadline and admission ownership through its owned-job cancellation cleanup; this criterion does not assert measured throughput or completed end-to-end/container/live verification.
