# FR-018: Apply Additional Per-Client Middleware

- **Status:** Active
- **Traces to:** [US-03](https://github.com/iteam7/gateway7/issues/32), [FR-003](FR-003.md), [ADR-002](../../architecture/adr/ADR-002.md)
- **Containers:** `gateway`

## Behavior

For an authenticated client with configured additional middleware, the gateway shall run the complete global middleware chain followed by that client's additions in their configured order.
Buffered response checks shall unwind the effective chain in reverse order.
A client shall not select, remove or replace global middleware through a request.

When a client has no additions, the gateway shall preserve the global middleware behavior.
When concurrent clients have different additions, one client's policy selection shall not change another client's effective chain.

When any client references an unknown, disabled, duplicate or already-global middleware instance, the gateway shall reject configuration before constructing plugin instances.
Configured instances shall have one shared startup/shutdown lifecycle regardless of how many client chains reference them.

The gateway shall apply the effective chain to native chat, Chat Completions and Responses requests, including checked streaming and explicit early streaming.
When an additional middleware lacks a required native or early hook, or refuses that delivery profile, the gateway shall reject the request before provider work rather than skip that policy.
Policy selection shall not add client identities or raw request content to plugin contexts, stored diagnostics or exported telemetry.

## Acceptance Criteria

### AC-01

Given two clients with the same model permissions and only the first client configured with an additional literal block policy, when both submit the blocked synthetic text, then the first receives HTTP 403 with no provider call and the second receives the synthetic provider answer.
A global block policy denies matching requests from both clients with no provider call.

### AC-02

Given a global tagging middleware and two ordered client additions, when the client sends a synthetic chat request, then request processing follows global, first, second order and response processing follows second, first, global order.
A client without additions runs only the global chain.

### AC-03

Given an unknown, disabled, duplicate or already-global additional middleware reference on an enabled or suspended client, when configuration is loaded, then validation fails before any plugin factory executes.
A shared valid additional instance is constructed, started and stopped once even when two clients use it.

### AC-04

Given clients with different policy chains, when they send concurrent requests through native chat, Chat Completions or Responses in supported buffered or early modes, then each request keeps its authenticated client's effective chain.
Missing required native or early hooks and response-dependent early policies fail before provider work.
Synthetic policy text and credentials do not appear in captured logs.
