# FR-019: Read Client Usage Through A Protected Operator Snapshot

- **Status:** Active
- **Traces to:** [US-13](https://github.com/iteam7/gateway7/issues/141) as a partial increment, [FR-012](FR-012.md), [ADR-003](../../architecture/adr/ADR-003.md)
- **Containers:** `gateway`

## Behavior

When an operator credential is explicitly configured, the gateway shall authenticate `GET /operator/usage` with that separate Bearer credential and return a numeric snapshot for its configured client identities.
The credential shall be resolved from the environment variable named by `auth.operator_token_env` and shall differ from the provider credential and every enabled client credential.
Operator access shall require client authentication to be enabled.
Missing, invalid or conflicting configured credentials shall prevent startup without exposing their values.
Without this configuration the endpoint shall return HTTP 404, including when a client supplies its own credential.
An operator credential shall grant no chat or model access, and a client credential shall grant no operator access.
Authentication shall happen before reading an operator request body, and successful snapshots shall use `Cache-Control: no-store`.

The snapshot shall describe this application process's lifetime since startup and shall reset when the application restarts.
For each configured client identity it shall contain provider-attempt counts, fixed provider outcomes (`complete`, `provider_error`, `cancelled`), known input and output token totals, and an independent count of attempts with unknown usage for each direction.
Identity shall come from the configured authenticated principal, never a prompt, header hint or middleware-editable payload.
Each provider attempt shall contribute once, including an attempt whose answer is later blocked by a response policy or whose observed usage precedes cancellation.
Its counters shall update at the provider attempt's terminal observation; in-flight admission is a separate signal.
A rejection before the provider is called shall add no provider attempt or tokens.
Unknown token usage shall stay explicitly unknown rather than becoming a measured zero.

The ledger shall retain aggregate numbers for at most the configured client set and shall not retain individual events, conversation text, tool contents, model history or credentials.
Client identities shall appear only in the authenticated operator snapshot, with no new client-identity labels in logs or metrics.
This snapshot shall not claim the arbitrary-period, per-model history of FR-012, durable storage, cross-process totals, hard token or currency budgets, monetary costs or billing reconciliation.

## Acceptance Criteria

### AC-01

Given the default configuration, when any caller reads `GET /operator/usage`, then it receives HTTP 404.
Given operator access enabled, when a caller supplies no credential, a client credential, a provider credential, duplicated Authorization headers or an invalid credential, then it receives HTTP 401 before its body is read.
The separate operator credential returns the snapshot with `Cache-Control: no-store` and receives HTTP 401 when used to call chat.

### AC-02

Given an explicitly selected operator token variable with a missing, malformed or reused value, when startup runs, then startup fails and no error contains that value.
Given operator access configured with client authentication disabled, then configuration validation fails.

### AC-03

Given client `client-a` with three observed provider attempts reporting input/output counts of `4/2`, `3/unknown` and `unknown/5`, when the operator reads its snapshot, then it shows three attempts, known input/output totals of `7/7` and one unknown attempt in each direction.
Concurrent observations shall not lose or duplicate increments, and mutation of a returned snapshot shall not change the ledger.

### AC-04

Given a request-side policy denial and a provider answer blocked by a response-side policy, then only the latter contributes one provider attempt and its known usage.
Successful, failed and cancelled provider attempts through buffered Chat, early Chat, buffered Responses and early Responses shall each contribute once.
Cancellation after valid source usage was observed shall retain that numeric accounting without replacing cancellation with success.

### AC-05

Given synthetic private prompts, answers, tools and credentials, then the ledger snapshot shall contain none of their content or values and metrics shall contain no newly introduced client-identity labels.
An unconfigured identity shall not create a ledger row.
After an application restart the snapshot shall have zero attempts and shall state its process-lifetime scope and reset behavior.
