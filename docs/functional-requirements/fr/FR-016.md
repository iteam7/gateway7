# FR-016: Limit Each Client's Active Requests

- **Status:** Active
- **Traces to:** [US-07](https://github.com/iteam7/gateway7/issues/36), operator capacity extension in [task #239](https://github.com/iteam7/gateway7/issues/239), [FR-006](FR-006.md), [ADR-003](../../architecture/adr/ADR-003.md)
- **Containers:** `gateway`

## Behavior

When an operator configures a concurrent-request limit for an authenticated client, the gateway shall apply that limit across native chat, Chat Completions and Responses, including buffered and early delivery.

When the client's capacity is occupied and global pipeline capacity is available, the gateway shall reject its next valid chat request with HTTP 429, code `client_overloaded` and a bounded `Retry-After` header before middleware or a provider call.

The gateway shall retain the client's capacity until its pipeline task, owned cleanup and response delivery have finished, without counting completed buffered delivery as an active global pipeline task.

When a client has no additional configured limit, the gateway shall retain the existing global pipeline-capacity behavior.

The gateway shall keep client counters local to one process, reset them on restart and exclude client identities from public metric labels and logs.

## Acceptance Criteria

### AC-01

Given clients `alpha` and `beta` each limited to one active request and a global limit of four, when `alpha` has one blocked request, then its next valid request returns HTTP 429 with `client_overloaded` and `Retry-After: 1`, while a request from `beta` can enter the pipeline.

### AC-02

Given the same client sends requests through different chat API shapes or delivery modes, when one request occupies its slot, then another shape receives the same client-capacity rejection before any additional provider call.

### AC-03

Given a buffered answer has finished generation but its HTTP body send is blocked, when another request from that client arrives, then it receives HTTP 429 while the global active-pipeline gauge is zero.
Given cancellation-resistant cleanup, the client slot remains occupied until that cleanup exits; after task-creation failure, the slot is available again.

### AC-04

Given no client-specific limit, requests retain the existing global HTTP 503 overload behavior.
Given two independent gateway applications or a restarted process, their counters are independent; this requirement establishes no distributed quota.
